## Idea A: generic guided notebook tour (first proposal)
Guided, clickable simulation of the real LabConstrictor experience, not a functional notebook; labelled "interactive preview, not a running scientific application". Five steps: 1 Launch the app (installed app icon, a browser window opening JupyterLab; the app runs locally, the browser is its interface); 2 Explore the Welcome notebook (simplified JupyterLab: sidebar, notebook tab, the real notebook-selection table); 3 Choose a notebook (select NucleiSky2DApp, click "Open the notebook"); 4 Interact with an analysis (representative controls from the real notebook, e.g. select a reference image, "Generate Random Crop"; simulated Run; optional Show/hide code); 5 See the result (precomputed aligned images, short explanation of the output and what the real app does). Based on the real template Welcome_template.ipynb and NucleiSky Welcome.ipynb / NucleiSky2DApp.ipynb; reuse NucleiSky docs/assets/2D_QC.jpg after checking it matches the example shown.
Options: (1) interactive HTML/CSS/JS mockup: low complexity, BEST; (2) JupyterLite: genuine in-browser Python on static hosting but is NOT the packaged app environment (native deps, system libraries, filesystem, multiprocessing limits), so misleading for microscopy apps; (3) real hosted JupyterLab: server, compute, sessions, security, not warranted. Do not add JupyterLite or hosted execution unless later testing shows visitors need to execute code.
Placement: dedicated /demo/, homepage invitation ("See the notebook interface") near How it works, a link from Use an app next to the Welcome notebook screenshot, optional link from app pages; NOT a sixth top-level nav item.
Files: scripts/lcsite/pages_demo.py, build_site.py, docs/assets/javascripts/demo.js, docs/assets/stylesheets/demo.css, pages_site.py (home entry), data/hubs.yaml (Use hub), DESIGN.md and tests. Known issue: scripts/check_design.py presently accepts content buttons only for copy and reset filters; demo buttons (Run, Open notebook, Reset tour) need a narrowly defined new permitted class, done as an explicit design-rule update, not by bypassing the checker. Estimate: proof of concept about a day; polished version several days (estimates).
Five constraints: honest simulation (persistent "Interactive preview, no scientific analysis is performed" label; examples precomputed); no credentials or uploads; representative not universal (NucleiSky example; each app can differ); accessible and mobile-friendly (native buttons, keyboard, focus management, stacked layout on phones); low maintenance (small versioned example; do not try to reproduce all of JupyterLab or sync arbitrary notebooks). Final check: usability test with a handful of biologists new to LabConstrictor: after the tour they should understand the app opens in a browser, you select and run notebooks, and calculations run in the installed app's local environment.

## Idea B: microscopy at the centre, napari and Fiji as alternative hosts (second proposal)
Recommended first example: the existing "Feature tour" tool in LabConstrictor-Playground: simple microscopy-style segmentation returning five outputs (label image, outlines, object centres, measurement table, summary) with controls intensity threshold and minimum object size. Its test uses a reproducible 256x256 synthetic fluorescence-like image and expects 16 objects at default settings. Visitor adjusts threshold, min object size, presses Run analysis, sees outlines on the image plus a measurement table; switching Notebook / napari / Fiji changes how the same inputs and outputs are presented, not the task. Interface table: Notebook (image preview, threshold + min-size controls, Run, figure and measurements under the cell); napari (realistic window with a LabConstrictor dock widget, image-layer selector, generated parameter form; label, outline, point layers over the image; measurement table); Fiji (open fluorescence image, Plugins > LabConstrictor > LabConstrictor Tools... dialog; label/overlay output, object ROIs, Results table). Key idea: a scientific function is declared once and the bridge adapts controls and outputs to each host. Actual references: LabConstrictor-Tools docs/img/N2_napari_form.png and F2_fiji_form_top.png.
"How does this work?" diagram: installed LabConstrictor app (scientific code + its Python environment) -> LabConstrictor-Tools bridge (discovers declared tools, generates forms, runs them in a separate process) -> Notebook | napari | Fiji native presentation. NOT a live connection from the website to Fiji/napari; a real connection happens on the researcher's computer after the app and host plugin are installed.
What is implemented today: Tools repo documents the bridge; Playground declares the Feature tour tool for hosts; napari and Fiji plugins are experimental (Linux testing incl. real apps; Windows/macOS not validated equally; Fiji needs a manual install/build route). The current Playground NOTEBOOK shows diagnostics and example-data generation but has no Feature tour analysis cell: to show one identical analysis across all three interfaces truthfully, add that small notebook example to Playground (a change in another repo).
NucleiSky registration (rotated higher-magnification field inside a larger image) is the more impressive example for a LATER version: prototype napari/Fiji screenshots exist and NucleiSky has a real notebook, but its App Centre manifest declares notebook support only; do not promote its napari/Fiji integration as generally available until validated and the manifest updated.
Recommendation B: one /demo/ page, client-side, small microscopy image with precomputed results, three interface tabs, editable controls, Reset demo; lightweight simulation with meaningful, consistent parameter changes; mobile simplified to analysis panel + output; homepage invitation "Try a microscopy analysis, no installation required" with a clear 'simulated' statement; real-looking image and meaningful output over window animation. Sequence: 1 build the segmentation example from Playground Feature tour; 2 add notebook, napari, Fiji views of the same analysis; 3 use existing host screenshots for authenticity; 4 explain the bridge and label it experimental; 5 consider NucleiSky registration as a second, more sophisticated example once host integrations are ready.
