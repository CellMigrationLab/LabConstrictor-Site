# Decisions by the maintainer (answers to the open questions, in order)

Raw material for the final plan. Each entry: the question, the answer, what it changes.

1. **Verified / Community badges: remove altogether.** (Asked 2026-10-11.) The App Centre will not show a Community or Verified tier. Consequences to carry into the final plan: remove the tier badge and legend from cards and app pages (`cards.py` is_verified/tier badge, `pages_apps.py` LEGEND and the Details row), the `verified_version`/`verified_on` registry fields and their schema/tests/docs (`content/submit.md` tier text, README, AGENTS.md, DESIGN.md badge colour rules); drop the App Centre plan's item 13 (trust-label definitions) and the docs plan's question on redefining Verified. No replacement trust label unless asked later.

2. **Missing scientific facts in a manifest: warn only, show "Not stated".** New fields (inputs, outputs, limitations, development status, quickstart, screenshot, docs link) are optional; build/problems.md lists what each app lacks; no app is delisted; no hard requirement until the six manifests are filled and the initialiser collects the fields.

3. **Demo scope: re-draw all three interfaces (Notebook, napari, Fiji) anyway**, as in the maintainer's own spec (`inputs/4a-demo-spec-nucleisky.md`), overriding the verified plan's recommendation of a staged notebook-first page. Carry into the final plan: keep the "Experimental integration preview" labels; build from the measured visual specs in `results/4-demo-and-video/investigate_reference-screenshots.json` (napari = stock dark theme tokens, Fiji = SciJava dialog, notebook = NucleiSky STYLE_CSS tokens); mitigate the verified risks (stale look-alikes, dead focusable controls, host views implying NucleiSky declares napari/Fiji support; its manifest says notebook only): date-stamp the views, no control that does nothing, hidden-until-JS controls, no-JS static figures. The demo plan's Stages 2-4 (real captures, video) still apply as later work. Open sub-question: which numbers to display (see decision 4).

4. **Demo data: the maintainer's real images, released NucleiSky code, existing masks (answers the dismissed question 4).** On 2026-10-11 the maintainer supplied `Image1.tif` (reference, 1266×2970, 1.3205 µm/px), `random_crop.tif` (query, 200×200, 1.1622 µm/px), and the two mask files (4387 and 30 nuclei) and asked to re-run the released code with them, without segmenting again, and to store web-friendly images. Done: `tools/demo_assets/` (generator) and `content/demo/` (WebP images + `example.json`). Result of the released code (adaptive matching, defaults, seed 0, deterministic): matcher quad (triangles and graph failed first), scale 0.9989, rotation −49.07°, 26 of 30 inliers, mean error 0.264 µm. Supersedes the synthetic fixture and the screenshot numbers for the demo. Open: provenance/licence of the images; whether the page may show the attempt sequence.

5. **Demo example: provenance and matchers.** Reference = Dataset 1 of the NucleiSky paper (HUVEC DAPI mosaic, Zenodo 10.5281/zenodo.20721416, **CC BY 4.0**, checked on the record); query made with NucleiSky's *Generate Random Crop*; masks from NucleiSky's threshold-and-watershed backend. The page should show each matcher's outcome. **Finding:** on this crop (30 nuclei) the released code with default settings succeeds only with **quad** (26/30 inliers, 0.264 µm); graph (1/30), triangles (none) and hashing (5/30) fail, independent of seed (8 seeds tested). The maintainer expected all matchers to succeed: open question whether a different crop (more nuclei / different zoom and angle) or a different configuration should be used, or the page shows the real mixed outcome. Do not tune settings to force success without recording them.

6. **Demo crop: keep the maintainer's own crop; show quad only; no more benchmarking (maintainer's instruction, 2026-10-11).** A search for another crop where all four matchers succeed was started and stopped at the maintainer's request (it had found that 3 of 18 seeded candidates satisfied all four with default settings, but none of that is used). The demo uses the supplied crop (made with *Generate Random Crop*) and displays only the quad result. The other matchers' failures stay recorded in `example.json` and are not shown on the page.
