# Fact-check of /how-it-works/ (read-only review)

Sources read from the default branches after `git fetch origin`: LabConstrictor `origin/main` 0066f5e (10 Oct 2026; also `origin/bridge-test` d107d9b), LabConstrictor_streamlit `origin/main` 8cbef3f, LabConstrictor-Tools `origin/main` 3fe5398, NucleiSky `origin/main` c8f8735 and `origin/bridge-test`, napari-labconstrictor / LabConstrictor-Fiji / LabConstrictor-QuPath `docs/user-guide.md` (origin/main). PyPI queried live. Site files: `data/how-it-works.yaml`, `content/how/*.html`, `content/submit.md`, `schema/labconstrictor-app.schema.json`, `scripts/lcsite/cards.py`, `pages_facts.py`, `content/how/how.js`.

Severity scale: wrong (false for the released product or contradicted by a source), overstated, unsupported (not in the guide the chapter links to, or not stated anywhere), wording.

## Problems

1. **Tool registration at install time is presented as how the installer works, but it exists only on development branches.** Severity: wrong for the released template; partly covered by the experimental notice, but the notice does not say it.
   - Sentences: "If your app declares tools, the same script registers them (see the bridge chapter)." (`content/how/installer.html`, stage 3, which carries no experimental notice); "The installer registers the app's tools on the computer; a failure to register never fails the installation." (`data/how-it-works.yaml`, chapter bridge, static); "At install time, a hook looks for `<package>_lc_tools` in the app's Python, installs the `labconstrictor-tools` package, and registers the app on the computer." (`content/how/bridge.html`, stage 1).
   - Source: `LabConstrictor origin/main:app/bash_bat_scripts/post_install.sh` and `.bat` contain no tools step (`git grep lc_tools origin/main` finds only the manifest schema's `hosts` description). The step exists only in `origin/bridge-test` (not merged: `git merge-base --is-ancestor` says no). `.tools/docs/tools_bridge.md` exists only on `bridge-test` and is titled "(optional, experimental: branch `bridge-test`)". NucleiSky `origin/main` has no `lc_tools` in `app/` or `construct.yaml`; only `NucleiSky/origin/bridge-test` does. `LabConstrictor-Tools docs/LABCONSTRICTOR_INTEGRATION.md:3-5`: "Implemented on the `bridge-test` branches ... Windows hooks have never been run on Windows"; line 41 adds "verifying ... the whole flow on macOS" as an open question. The site's own `data/demo.yaml:39,44` already says it correctly ("exists on development branches", "In the experimental version of the installer", "tested on Linux only"). The user guide `LabConstrictor-Tools docs/user-guide.md:12` states registration as fact, so the page follows the guide, but the guide is itself ahead of the released template.
   - The page's caveat covers only Windows ("The Windows hooks have not yet been run on Windows."), and only in the panel, not in the static summary. macOS is also unverified.
   - Suggested (installer, stage 3): remove the sentence, or: "In the experimental version of the installer, an app that ships a tools module is also registered for the plugins (see the bridge chapter)."
   - Suggested (bridge static): "In the experimental version of the installer, the app's tools are registered on the computer at install time; a failure to register never fails the installation. The installer in the released template does not do this yet."
   - Suggested (bridge, stage 1): add "In the experimental installer (a development branch of the template, not in released apps). It has been run on Linux only: the Windows hooks have never been run on Windows and macOS is not verified." The hook installs `labconstrictor-tools` from its GitHub archive by default, because the package is not on PyPI (PyPI returns 404 for `labconstrictor-tools`), so it needs internet at that moment.

2. **The experimental notice is softer than the plugin guides.** Severity: overstated safety (and the site rule forbids claims about stability).
   - Sentence: "Experimental. The plugins are untested on some systems and may change; each plugin's guide says what stage it is at." (`content/how/tools.html`, `content/how/bridge.html`); also "The plugins are experimental and untested on some systems" (yaml, bridge, static).
   - Source: `LabConstrictor-Tools docs/user-guide.md:7-8`: "Under heavy construction. The napari, Fiji and QuPath plugins are untested and unlikely to be stable. Expect bugs, missing features and changes without notice." napari guide line 8: "Tested on Linux. Windows and macOS are untested." Fiji and QuPath guides: "untested and unlikely to be stable". "Untested on some systems" implies they are tested elsewhere, which is true only for napari on Linux.
   - Suggested: "Experimental. The plugins are under heavy construction: untested and unlikely to be stable. Expect bugs and changes without notice. Each plugin's guide says what stage it is at."

3. **"Your users do not need Python, pip or a terminal."** (`data/how-it-works.yaml`, chapter installer, text.) Severity: wrong for Linux, misleading elsewhere.
   - Source: `install.md:25-27` (Linux): "Open a terminal in the download folder and run `bash` ..." `notebook_usage.md` section 2: "When you start the application, a terminal will pop up ... Do not close the terminal". `app/menuinst/notebook_launcher.json` has `"terminal": true`. `install.md:7`: a command prompt window opens during installation on Windows. The site's own demo says "A terminal window opens and has to stay open" (`content/demo/windows/notebook.html`).
   - Suggested: "Your users do not need to install Python or pip. On Linux they run the installer from a terminal, and a terminal window stays open while the app runs."

4. **Deposit: the form "checks your notebook".** Severity: overstated against the form's code.
   - Sentences: "A web form checks your notebook and requirements.yaml and opens a pull request ... an automatic workflow then checks the notebook again after you merge it." (yaml, chapter text); "Validate & Add Submission checks the notebook and the requirements." (`content/how/deposit.html`, stage 2).
   - Source: `LabConstrictor_streamlit app.py:1029-1044`: the button only tests that a notebook and a requirements file were uploaded, then calls `validate_requirements()` (`app.py:93-112`), which checks only the requirements file. No notebook content is validated in the update view. The form's intro text (`app.py:1001`) says "This will validate the notebook and requirement", so the page repeats the form's own wording, which the code does not back. The "again" in "checks the notebook again" therefore also overstates.
   - Suggested: "Validate & Add Submission checks the requirements file (and that both files are there). If it passes, the notebook is added to the submission list." Chapter text: "A web form checks your requirements.yaml and opens a pull request in your repository; an automatic workflow then checks the notebook and its dependencies after you merge it."

5. **Deposit/requirements: what the form actually accepts.** Severity: unsupported by the guide / omission that matters to authors.
   - `app.py:98-109`: the only required key is `dependencies`, and every entry must be `package==version` (regex `^[a-zA-Z0-9_.-]+==[a-zA-Z0-9_.-]+$`); `>=` or an unpinned name is refused. `app.py:972-977, 1137-1142`: only a classic token starting with `ghp_` is accepted; a fine-grained token (`github_pat_`) is refused.
   - Page: "dependencies: every package the notebook uses, with its version" and "A token is a password-like code you create on GitHub" say neither. Suggested additions: "Each dependency must be pinned with == (for example pandas==2.2.2)." and "The form needs a classic token (starting with ghp_)."
   - "This is the example from the guide. Real files may carry more fields." (`requirements.html`): the guide (`notebook_requirements.md:38-42`) says the file "must contain" the three fields and mentions no others. It is true of real files (NucleiSky's `requirements.yaml` has `windows_dependencies`, `linux_dependencies`, `macos_dependencies`; `.tools/python/merge_requirements.py` documents them), but it is not in the guide. Severity: unsupported (true). Either cite the OS-specific fields or drop the sentence.
   - Also `notebook_upload.md:143` says "Click **Validate submission**", while the real update form says "Validate & Add Submission" (`app.py:1029`; "Validate submission" is the initialise form's button, `app.py:915`). The page's label is right; the guide is out of date (fix in the template).

6. **Code chapter: "pip package" and "both" are not in the linked guide.** Severity: unsupported by the guide; the NucleiSky example is verified.
   - Sentences: "A pip package: its name goes into the notebook's requirements.yaml and is installed from PyPI." / "Both: for example the desktop app uses the code in src while a Colab run installs the published package." (yaml); panel `where:pip` says "published somewhere pip can find it" (inconsistent with "from PyPI").
   - Source: `external_code_upload.md` covers only `src/` and `__init__.py`; it never mentions pip packages, PyPI or Colab. `app_manifest.md:27` only says `pip: my-app  # the name on PyPI` (a manifest field). Technically true: `post_install.sh:47` runs `pip install -r requirements.txt`, and `construct.yaml` carries `src` as `extra_files`. The form accepts only `name==version` pins.
   - Suggested: "A pip package: list it in requirements.yaml with a pinned version (name==version); the installer's pip installs it with the other packages." Keep "Both" but mark it as an example. Suggested NucleiSky wording: "NucleiSky does this: the desktop app installs its code from src, and its Colab notebooks run `pip install nucleisky[all]` from PyPI."
   - NucleiSky claim: verified (see the verified list below). One precision: PyPI holds only version 0.0.1 of `nucleisky`, so a Colab run installs the latest published release, not necessarily the code currently in `src`.
   - "the app's installer carries it" (panel `where:src`) is not in the guide but is true (`construct.yaml` `extra_files`; `post_install` installs it when `setup.py` is bundled).

7. **Portable chapter.**
   - "Run Colab-only setup only on Colab, and the same notebook works in both." Severity: overstated. The guide (`notebook_portability.md:127-132`) adds paths, Colab forms and testing in both. Suggested: "...so the notebook does not fail outside Colab. Test it in both before you release."
   - "many people also like to open them in Google Colab" Severity: wording, a popularity-type claim. The guide says "many collaborators and reviewers prefer Google Colab" (line 3). Suggested: "Collaborators and reviewers often use Google Colab for quick cloud runs."
   - Panel, hidden state: "▶ Data input (the cell's code is hidden; the play button runs it)". Severity: unsupported/overstated. `code_hiding.md:17` (file line numbers): "Depending on the versions of JupyterLab and ipywidgets you use, ... a play button *might* show up"; it also says you can always run the cell with the toolbar play button. Nothing in the guide says a hidden cell shows its `# @title` text as a heading. Suggested: "(the cell's code is hidden; a play button may appear next to it, depending on versions; the toolbar play button always works)", and drop the "▶ Data input" title line or mark it as an assumption.
   - The Colab code sample is an abridged copy of the guide's example (the `userdata` import and the `instanseg-torch` install are omitted) without saying so. Severity: wording; add "(shortened from the guide)".

8. **Packaging.**
   - Release asset list (`content/how/packaging.html`, stage 4): exe, 2 x pkg, sh. Real releases carry more: NucleiSky 0.1.1 has `...-Windows-x86_64.msi` and `...-MacOSX-arm64.sh` / `...-MacOSX-x86_64.sh` besides the four listed (`installer_type: all`, `construct.yaml:5`). The guides name only .exe/.pkg/.sh (`before_getting_started.md`). Severity: wording; the panel says "an illustration", but adding "for example" and "(a release can hold more file types)" would be safe. The naming pattern `Name-version-OS-arch.ext` is right (schema description also says so).
   - "Two more workflows run when you change notebooks or code" (stage 4). Severity: wording. There are `update_on_notebook_change.yml` (push to `notebooks/**`), `update_on_src_change.yaml` (push to `src/**`), `check_app_manifest.yml` (manifest changes and release publish) and the weekly `sync_template.yml`. Suggested: "Other workflows run when you change notebooks, code or the app description; a weekly one can keep your repository in step with the template (after a one-time token setup, see the template-synchronization guide)."

9. **Installer chapter details not in the linked guide.** Severity: unsupported by `install.md`, true or partly true in the code.
   - "The wizard asks for the installation type (on Windows: Just Me, recommended, or All Users) and the folder, and offers to create shortcuts." `install.md` says only "Follow the on-screen prompts" (macOS: "we recommend Install only for me"; Linux: prompts in the terminal, not a wizard). The Windows details match the site's own demo, built from the real installer. Suggested: "On Windows the setup wizard asks ... ; macOS and Linux installers ask similar questions in their own way."
   - "(GPU versions when an NVIDIA GPU is detected, otherwise the CPU ones)". `post_install.sh:33-44`: on macOS the CPU list is always used; on Linux and Windows the test is whether `nvidia-smi` is found (`post_install.bat:58-68,177-191`), and a GPU file is used only if `requirements_gpu.txt` exists. Suggested: "(on Windows and Linux, the GPU list when the NVIDIA tool nvidia-smi is found; otherwise, and on macOS, the CPU list)".
   - "This needs an internet connection and can take a while." Not in `install.md` (it says "about 6-8 minutes"), but true because pip downloads the packages (`post_install.sh:47`). Suggested: "It takes about 6-8 minutes and needs an internet connection".
   - "installs ... when the app has one, the package from `src`": verified (`post_install.sh:65-71`, only if `setup.py` is bundled).

10. **Manifest and share chapters.**
    - "The site shows only what the file says, and writes "Not stated" for what it leaves out." (`manifest.html`) and "what the manifest leaves out is shown as "Not stated"" (`share.html`, stage 4). Severity: overstated. `submit.md:47`: "the page says 'Not stated' or leaves it out". In code: status and license say "Not stated" (`pages_facts.py:40`, `pages_apps.py:40`), inputs/outputs say "not stated by the author" only for scientific kinds (`pages_facts.py:27`), and limitations are simply left out (`pages_facts.py:34`).     - "Open the submission form on this site" (`share.html`, stage 2). Severity: wording/inaccurate. Suggested: "Open the submission form (a GitHub issue) from the Submit page".
    - The manifest panel lets a visitor switch all three ways to get the app off, which draws `distribution:` with nothing under it and a card with no route badge.     - The mock card shows the kind as a badge ("Analysis"). Real cards show it as small text under the name (`cards.py:149`); only the route badges (Desktop, Colab, pip) are badges. Severity: wording.
    - Static: "Optional fields add ... status, screenshots ..." vs `submit.md:44-48`, where status, quickstart, screenshots, inputs and outputs are "Recommended" and limitations, DOI and others "Optional". 11. **Tools chapter.**
    - "The type hints of a function are the whole declaration." (yaml, chapter text). Severity: overstated. A tool also needs the `@tool("...")` marker and the module named `<package>_lc_tools` (AUTHORING.md:9,29-31); the page's own bullet says so.     - Chapter title "Declare tools ... (the plugin manifest)" can be confused with the app manifest (`labconstrictor-app.yaml`) two chapters later. Severity: wording; the Tools docs call it "the manifest" too, so this is a choice, but "tool declaration" is safer.

12. **Link labels differ from the guide titles** (rule: "Menu titles ... are the page's own first heading"). Severity: wording. "Write notebooks for Colab and JupyterLab" vs the title "Write notebooks that run in both Google Colab and JupyterLab"; "Use apps in your image software" vs "Use apps inside napari, Fiji and QuPath" (the first is the docs group's name, `data/guides.yaml:19`). ## Statements verified as correct

- Chapter portable: Colab-only setup (Drive mount, `!pip`) guarded by `if 'google.colab' in sys.modules`; `# @title` at the top of a cell gives a Colab header and stays visible in JupyterLab; longer explanations belong in Markdown cells (`notebook_portability.md:16-28`). The printed messages in the panel match the guide's code. The JupyterLab fallback output is the guide's `else` text.
- Chapter code: a folder under `src` with `__init__.py` becomes an importable package; each imported folder needs its own `__init__.py`, which can be empty (`external_code_upload.md:160-173`). **NucleiSky "built this way": true.** `construct.yaml` (NucleiSky main) lists `src/nucleisky/**` and `setup.py` under `extra_files`; `requirements.yaml` and `requirements.txt` do not list `nucleisky`; the Step 0 cell of `NucleiSky2DApp.ipynb` (`# @title Initialize Environment & Install Dependencies`) runs `!pip install -q --upgrade nucleisky[all]` only inside `if 'google.colab' in sys.modules`; `https://pypi.org/pypi/nucleisky/json` returns 200, version 0.0.1 (uploaded 2026-06-30), same as `pyproject.toml`.
- Chapter requirements: the Generator notebook is run in the same environment as the notebook (locally) or in Colab; the Validator is best in Colab; example content, the hyphen-and-space list rule and the three fields `dependencies`, `python_version`, `description` (`notebook_requirements.md:12-65`).
- Chapter deposit: labels "Upload/Update notebook", "Upload/Update notebooks on an existing project", "Jupyter Notebook file (.ipynb)", "Requirements yaml file (requirements.yaml)", "Validate & Add Submission" with the ➕ icon, "📃 Submission list", "🗑️ Remove", "⬆️ Upload it to GitHub", "GitHub repository URL", "Personal Access Token", "🚀 Create pull request", and the error text "Please upload a Jupyter Notebook file." all match `app.py` (lines 849, 997, 1009, 1021, 1029, 1033, 1085, 1096, 1106, 1113-1128). "Create pull request" is disabled until a repository address is given (`app.py:1127`). Several notebooks can be queued and removed. The undo claim is true: `update_on_notebook_change.yml:146-154` reverts the merge commit (`git revert ... -m 1`) when any step fails on a push, after verifying the merged requirements in a conda environment. (Nuance: it is a revert commit, and the conda check can be skipped by the repository variable `SKIP_CONDA_ENV_TEST`.)
- Chapter packaging: workflow name "Build Release Installers"; started when a release is published (`release_constructor.yml:1-8`; also by manual run); builds Linux, macOS arm64 and Intel, and Windows; installers are uploaded to the release's assets (`:184-188`); wait for running workflows (`executable_creation.md:5-7`, verbatim); tag in MAJOR.MINOR.PATCH form, example 0.0.1, title "Initial release", description optional; file-name pattern `Name-version-OS-arch.ext` (confirmed on NucleiSky 0.1.1: `NucleiSky-0.1.1-Windows-x86_64.exe`, `-MacOSX-arm64.pkg`, `-Linux-x86_64.sh`); the workflow-status guide explains failures; the weekly template sync exists (`sync_template.yml`, Monday 09:00 UTC).
- Chapter installer: not code-signed, so the system may warn (`install.md:5,12`); private conda environment; post-install script installs the requirements list then the package from `src` when bundled; the app appears in the Start menu / Applications folder / applications menu; opening it starts JupyterLab in the browser with the Welcome notebook, which lists the app's notebooks (`notebook_usage.md` sections 1, 2, 4). The demo part is called "1. Install the app (Windows)" (`pages_demo.py:32`).
- Chapter manifest: required fields `schema`, `name`, `summary`, `kind`, `distribution`; routes installer / colab (label + url) / pip (PyPI name); the check workflow never blocks installers and also runs on release publish (`check_app_manifest.yml:1-9`; `app_manifest.md:112-115`); route badges "Desktop", "Colab", "pip" are the real ones (`cards.py:11`).
- Chapter share: public repository with a licence; manifest in the root; latest release carries installers; Colab links on colab.research.google.com and the author chooses which are listed; a bot checks and opens a pull request; a maintainer merges; app appears at the next daily build; only a pointer is stored; no resubmission needed for a new version (`submit.md:50-60`).
- Chapter tools: the type mapping (float/int number, bool check box, Literal/Enum dropdown, Image chosen in the host, Table a CSV file; NumPy array / pandas DataFrame received) (`AUTHORING.md:35-42`); `Min(0)` enforced; "everything beyond the types is optional ... a host that does not know a hint shows a plain, working form" (`AUTHORING.md:185`, `MANIFEST.md:9`); `@tool`, `<package>_lc_tools` next to the package; the example imports (`Image, ImageOut, Min, Table, tool`) all exist in the docs; an `ImageOut` becomes a layer (napari) or window (Fiji) (`HOST_FEATURES.md:20`; QuPath shows a preview, not mentioned on the page).
- Chapter bridge: menu paths are exact in all three hosts ("Plugins > LabConstrictor tools" in napari, "Plugins > LabConstrictor > LabConstrictor Tools..." in Fiji, "Extensions > LabConstrictor tools..." in QuPath: `user-guide.md:15-17` and each plugin's guide); the tool runs in the app's own Python environment in a separate process, so apps with conflicting dependencies can live side by side (`user-guide.md:5`); output kinds: image → layer/window, table → table, points → points layer / point ROIs / point annotations (`AUTHORING.md:69`, `HOST_FEATURES.md:24`); files are listed by the host (`MANIFEST.md`, `FileOut`); in the experimental hooks "a failure here never fails the installation" and the note goes to `menuinst_debug.log` (`LABCONSTRICTOR_INTEGRATION.md:19-24`; code in `bridge-test:post_install.sh`); "The Windows hooks have not yet been run on Windows" (`LABCONSTRICTOR_INTEGRATION.md:4`). The hook looks for `<package>_lc_tools` and installs and registers as described, but see problem 1 for its status.
- Experimental notice present where plugins are described: chapter text of tools and bridge, and the banner inside both panels. The installer chapter's mention of tool registration has none (problem 1).
- Page links resolve in the built site (`../guides/...`, `../demo/`).
